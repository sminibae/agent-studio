# Engineering

이 문서는 코드 작성 및 검증 규칙을 정의한다.

이 문서의 명령어 절은 **아직 확정되지 않았다.** 프로젝트의 기본 구조를 만들기 전이므로 현재는 방향만 제시한다. 기본 구조를 만든 뒤 실제로 동작하는 명령으로 교체하며, 그전에는 아래 명령을 그대로 실행하지 않는다.

---

## Python

### 스타일

- Google Python Style Guide를 따른다.
- 모든 함수와 메서드에 예외 없이 타입 어노테이션을 붙인다.
- docstring은 Google 스타일로 쓴다. 공개 함수, 클래스, 모듈에 붙인다.
- 줄 길이는 Ruff 기본값(88)을 따른다.

### 도구

| 도구 | 역할 |
| --- | --- |
| uv | 패키지·가상환경 관리 |
| Ruff | 린트 + 포매팅 |
| mypy | 정적 타입 검사 (strict) |
| pytest | 테스트 |

- Ruff 하나로 린트와 포매팅을 모두 처리한다. Black을 따로 두지 않는다.
- mypy는 처음부터 strict 모드로 사용한다. 개발이 진행된 뒤 strict 모드를 적용하면 기존 타입 오류를 한꺼번에 수정해야 한다.
- `Any`가 필요한 경우에는 주석으로 이유를 남긴다. JSONB 경계처럼 불가피한 곳에서만 제한적으로 사용한다.

### Pydantic

- 외부와 주고받는 모든 데이터는 Pydantic 모델로 검증한다. API 요청과 응답, JSONB 컬럼의 내용, 모델 Provider의 응답이 이에 해당한다.
- JSONB 컬럼은 읽을 때와 쓸 때 모두 검증한다. 쓰기만 검증하면 과거 데이터가 현재 구조와 맞지 않을 때 오류를 즉시 발견하기 어렵다.
- API 스키마와 도메인 객체를 같은 클래스로 쓰지 않는다.

## TypeScript

### 스타일

- strict mode를 켠다.
- `any`를 쓰지 않는다. 타입을 모르면 `unknown`으로 받고 좁힌다.
- 컴포넌트 props에 명시적 타입을 붙인다.

### 도구

| --- | --- |
| ESLint | 린트 |
| Prettier | 포매팅 |
| tsc | 타입 검사 |

## 테스트

### 계층별 방침

| 계층 | 무엇을 검증하나 | 비중 |
| --- | --- | --- |
| Unit (Domain) | 불변식, 상태 전이, 지표 계산식 | 가장 많이 |
| Service (Application) | 유스케이스 흐름, 트랜잭션 경계 | 많이 |
| API | 요청·응답 계약, 상태 코드, 오류 형식 | 보통 |
| E2E | 핵심 흐름 몇 개 | 적게 |

### 반드시 테스트할 것

도메인 규칙은 평가 결과의 재현성과 신뢰성을 보장한다. 다음 규칙은 반드시 테스트한다.

- Definition Version이 생성 후 수정되지 않는다
- Setup이 생성 후 수정되지 않는다
- Definition을 수정해도 기존 Setup과 실행 이력이 변하지 않는다
- Repeats N이 Run N개를 만든다
- Run 상태가 Case Run 상태들로부터 올바르게 유도된다
- 재시도가 새 Case Run을 만들지 않는다
- 지표 계산식의 분모가 `docs/analytics.md` 정의와 일치한다
- 실패한 Case Run이 집계에서 누락되지 않는다

특히 마지막 두 항목을 주의한다. 지표의 분모가 잘못되면 결과가 왜곡되어도 이를 알아차리기 어렵다.

### 테스트 작성 방침

- DB가 필요한 테스트는 실제 PostgreSQL을 쓴다. SQLite로 대체하지 않는다. JSONB와 제약조건 동작이 다르다.
- 모델 API 호출은 테스트에서 mock한다. 실제 호출은 별도 태그를 붙여 분리하고 기본 실행에서 제외한다.
- 테스트 이름은 검증하는 규칙을 문장으로 쓴다. `test_editing_definition_does_not_change_existing_setup`처럼.

## 명령어

**아직 확정되지 않았다.** 프로젝트의 기본 구조를 만든 뒤 실제 명령으로 교체한다.

Makefile을 공통 진입점으로 사용한다. 백엔드와 프런트엔드의 명령이 다르므로 저장소 루트에서 두 영역의 작업을 함께 실행할 수 있어야 한다.

```
make fmt         # 포매팅
make lint        # 린트
make typecheck   # 타입 검사
make test        # 테스트
make check       # 위 전부
```

각 명령은 다음 작업을 실행할 예정이다.

```
# backend
uv run ruff format .
uv run ruff check .
uv run mypy .
uv run pytest

# frontend
pnpm lint
pnpm typecheck
pnpm test
```

작업을 마치기 전에 `make check`를 실행한다. 이 규칙은 `.claude/CLAUDE.md`에도 있다.

프로젝트의 기본 구조를 만들면 이 절을 실제 명령으로 바꾸고, 자주 사용하는 명령은 `.claude/CLAUDE.md`에 요약한다.

## 마이그레이션

- 스키마 변경은 반드시 Alembic 마이그레이션으로 한다. 손으로 DDL을 실행하지 않는다.
- 마이그레이션은 되돌릴 수 있게 작성한다. `downgrade`를 비워 두지 않는다.
- 데이터 이관과 스키마 변경은 서로 다른 마이그레이션으로 작성한다. 하나의 마이그레이션에서 함께 처리하면 실패했을 때 중간 상태가 남을 수 있다.

## Git

- 커밋 메시지 제목은 명령형 한 줄로 쓴다.
- 도메인 용어를 커밋 메시지에서도 그대로 쓴다. `docs/domain-model.md`의 용어를 따른다.
- 하나의 커밋은 하나의 변경 의도를 담는다. 포매팅 변경과 로직 변경을 같은 커밋에 섞지 않는다.

## 열린 질문

- **패키지 매니저.** 백엔드는 uv로 정했다. 프런트엔드는 pnpm을 전제하고 썼으나 확정되지 않았다.
- **CI.** GitHub Actions를 사용할지와 어떤 단계를 포함할지는 정해지지 않았다. 어떤 도구를 선택하더라도 최소한 `make check`를 실행해야 한다.
- **테스트용 PostgreSQL 실행 방식.** Docker Compose로 띄울지, testcontainers를 쓸지 정해지지 않았다.
- **커버리지 기준.** 숫자 목표를 둘지 정해지지 않았다. 위의 "반드시 테스트할 것" 목록이 숫자보다 실질적이다.
